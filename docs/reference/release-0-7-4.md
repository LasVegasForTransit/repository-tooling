# Repository tooling 0.7.4

Typed Worker version previews can now build pull request code without deployment credentials and
publish the retained compiled payload from a separate trusted default-branch workflow. The publisher
validates the successful source workflow, current open same-repository PR, exact commit, and
retained artifact before uploading. It ignores PR deployment configuration, imports no PR code,
rejects runner-file imports, and uses only the trusted preview bindings. No PR SQL migrations or
production activation run in this path.

Callers opt in with `release-pr-preview-build.yml` and `release-pr-preview-publish.yml`. The
existing combined workflow remains available for callers that have not migrated, including named
Durable Object previews. Restrict the migrated preview and production GitHub environments to the
selected `main` branch and remove deployment credentials stored at repository scope.

Platform manifests can declare `github.environments` with an environment name and its one allowed
branch. Production preflight reports drift, and bootstrap applies the restriction while preserving
existing reviewer and timer protections. Unexpected existing branch rules require deliberate
reconciliation.

Schema migration steps accept a separate `CLOUDFLARE_MIGRATIONS_API_TOKEN` so account-level D1
permissions do not have to be added to a per-Worker deployment token. Existing callers retain their
credential fallback until they rotate.

All shared package and example references advance to 0.7.4. Applications can adopt the reviewed
source commit with the standard updater; publishing or tagging remains a separate maintainer action.

Isolated previews require separate preview resources. They reject `previewReadOnlyBindings`: a
read-only facade generated by an untrusted PR cannot safely limit access to a production bucket. The
publisher copies only the verified static assets into the trusted browser suite's expected `dist`
directory; acceptance code always comes from `main`.
